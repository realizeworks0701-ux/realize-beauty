# Settings - Plan

## 概要

契約プランの確認・変更と、お支払い方法の管理を行う（[ADR-029](../decisions/ADR-029-subscription-billing.md)）。

設定画面（[settings.md](settings.md)）の「プラン・お支払い」カードから遷移する。

カード情報は Stripe Checkout・Stripe カスタマーポータル（いずれも Stripe がホストする画面）で入力し、RB のサーバには一切到達しない。本ページが扱うのは「どのプランを契約しているか」だけで、請求金額の計算・日割りは行わない（すべて Stripe に委ねる）。請求書・領収書・支払い履歴もカスタマーポータルへ委ね、本ページには持たない。

**本ページと契約系APIはプラン制限（`feature` ミドルウェア）の対象外**とする。契約が切れて全機能が使えなくなったサロンが、再契約の導線にたどり着けなくなるため。サイドバーの「設定」からは契約状態に関わらず常に到達できる。

Stripe Checkout・カスタマーポータルからの戻り先も本ページ（`BILLING_RETURN_PATH` の既定値 `/settings/plan`）。

---

## Route

`/settings/plan`

`meta.feature` は付けない（未契約でも開ける唯一の業務画面のため）。

---

## Components

### お支払い警告バナー

`subscription.needs_payment_attention` が true のとき、ページ最上部に警告 Message を表示する。

| status | 表示 |
|------|------|
| past_due（お支払い確認中） | 「お支払いを確認できませんでした。カード情報をご確認ください。再試行中のため、機能は引き続きご利用いただけます」 |
| unpaid（利用停止中） | 「お支払いを確認できないため、ご利用を停止しています。お支払い方法を更新してください」 |
| incomplete（お支払い手続き未完了） | 「お支払い手続きが完了していません。お手続きを最後までお進めください」 |

* いずれもバナー内に「お支払い方法を管理」ボタンを併記する（カスタマーポータルへ遷移）
* past_due と unpaid の違い（再試行中は使える／回収フローが尽きると停止）を文言で明示する。ユーザーが最も自力で復旧しやすい状態のため、この2つは同じ扱いにしない

### 現在のプランカード

GET /api/v1/subscription の `subscription` に応じて表示を切り替える。

| 状態 | 表示 |
|------|------|
| 契約なし（`subscription` が null、または `is_active=false`） | 「現在ご契約中のプランはありません」＋「下のプランからお選びください」の案内。過去に契約していた場合（`subscription` があり `status=canceled`）は「{plan_label}（{status_label}）」と終了日（`ended_at`）も併記する |
| 利用中（`is_active=true`） | プラン名（`plan_label`）＋月額（`monthly_price`）＋状態 Tag（`status_label`）＋今期の利用期間 |
| トライアル中（`status=trialing`） | 上記に加えて「トライアル終了日: {trial_ends_at}」 |
| 解約申請中（`cancel_at_period_end=true`） | 警告色 Tag「解約申請中」＋「{current_period_end} までご利用いただけます。以降は自動で停止します」＋「解約を取り消す」ボタン |

* 利用期間は `current_period_start` 〜 `current_period_end` を日付で表示する。解約申請がないときは「次回更新日: {current_period_end}」と読み替えて表示する
* 状態 Tag の文言は `status_label`（サーバが返す日本語ラベル）をそのまま使い、フロントで status を読み替えない
* レスポンス直下の `plan` は「いま実際に機能が使えるプラン」（失効時は null）、`subscription.plan` は契約行に残るプランで、**両者は一致しないことがある**（解約済み・未払いなど）。機能の出し分けは常に `features` を見る

### プラン一覧

`plans`（GET /api/v1/subscription）をそのまま3枚のカードとして横並びに表示する。金額・機能はサーバの値を使い、フロント側に定義を持たない（`config/billing.php` が単一の正）。

| プラン | 月額（税込） | 使える機能 |
|------|------|------|
| Lite | 980円 | 顧客管理／カルテ管理／写真管理 |
| Standard | 1,980円 | Lite の機能＋予約管理／Googleカレンダー連携／LINE連携 |
| Pro | 3,980円 | Standard の機能＋AI要約／高度な分析 |

* 機能名は Feature のラベル（顧客管理・カルテ管理・写真管理・予約管理・Googleカレンダー連携・LINE連携・AI要約・高度な分析）を使い、バックエンドの `Feature::label()` と一字一句揃える
* 各カードは「そのプランで新たに使えるようになる機能」を強調し、下位プランから引き継ぐ機能は「Lite のすべての機能」のようにまとめる
* 契約中のプランのカードには「ご利用中」Tag を表示し、ボタンを出さない（「現在ご利用中のプランです」とだけ添える）
* ただし契約が生きていない間（未契約・解約済み・利用停止・Stripe 未接続）は、**現在のプランを含む全プランに「このプランで開始」を出す**。ここを塞ぐと再契約もバックフィル状態からの本契約もできなくなる
* `is_purchasable=false`（Stripe Price ID 未設定）のプランはボタンを無効化し「準備中」と表示する。設定漏れをユーザー操作で顕在化させない
* ボタンのラベルは契約状態で変える

| 契約状態 | ボタン | 遷移 |
|------|------|------|
| 契約なし | 「このプランで始める」 | Stripe Checkout へ外部遷移 |
| 契約中（他プラン） | 「このプランに変更」 | 確認ダイアログ → プラン変更API（画面内で完結） |
| 契約中（同一プラン） | 「ご利用中」（無効） | — |

### 契約開始（Stripe Checkout）

1. 「このプランで始める」→ POST /api/v1/subscription/checkout（送るのは plan key のみ）
2. レスポンスの URL へ**同一タブで遷移**する（別タブは復帰時のクエリ処理が二重になるため使わない）
3. Stripe がホストする Checkout でカード情報を入力
4. 完了・中断のいずれでも本ページへ戻る（[復帰時のクエリパラメータ処理](#復帰時のクエリパラメータ処理)）

* ボタン押下から遷移までは押下ボタンをローディング表示＋無効化する（多重発行防止）
* すでに契約中の場合はサーバが 422（「すでに契約中です。プラン変更をご利用ください。」）を返す。画面側でもボタンを「このプランに変更」に切り替えて、この経路に入らないようにする

### プラン変更

* 「このプランに変更」→ 確認ダイアログ → POST /api/v1/subscription/change-plan
* 即時反映。差額は Stripe の日割り（`create_prorations`）で精算され、**RB 側で金額を計算・表示することはしない**
* 確認ダイアログの文言は方向で変える
  * アップグレード: 「{変更先}プランに変更します。差額は日割りで計算され、次回のご請求に反映されます。よろしいですか？」
  * ダウングレード: 「{変更先}プランに変更すると、{使えなくなる機能}がご利用いただけなくなります。**顧客・カルテ・写真のデータは削除されません**。差額は次回以降のご請求に充当されます。よろしいですか？」
* 「使えなくなる機能」は現在のプランにあって変更先に無い機能を Feature のラベルで列挙する（例: 予約管理・Googleカレンダー連携・LINE連携）
* ダウングレードしても LINE の認証情報・Googleカレンダーの接続は保持され、再契約でそのまま復帰する旨をダイアログに添える
* 成功後は GET /api/v1/subscription を再取得し、**あわせて GET /api/v1/auth/me も再取得**する。サイドバーの表示とルートガードは `user.features` を見るため、ここを更新しないと画面と権限がずれる
* 同一プランへの変更はサーバが 422（「すでにこのプランをご契約中です。」）を返す

### 解約

* 「解約する」ボタン（Danger・契約が生きている（`is_subscribed` かつ `is_active`）かつ `cancel_at_period_end=false` のときのみ表示）
* 確認ダイアログ: 「解約すると {current_period_end} をもってご利用が停止します。期間終了までは通常どおりご利用いただけます。**顧客・カルテ・写真のデータは削除されません**。再契約すればそのままご利用を再開できます。よろしいですか？」
* 確定で POST /api/v1/subscription/cancel → `cancel_at_period_end=true`。**即時停止はしない**
* 期間終了時に Stripe が status を canceled にし、webhook 経由で利用停止になる。RB の画面上で即座に機能が消えるわけではない旨を注記する
* 申請済みの状態でもう一度呼ぶとサーバが 422（「すでに解約を申請済みです。」）を返す

### 解約の取り消し

* 「解約を取り消す」ボタン（`cancel_at_period_end=true` のときのみ表示）→ POST /api/v1/subscription/resume
* 確認ダイアログは出さない（利用を継続する方向の操作で、取り返しがつくため）
* 成功後は現在のプランカードを「利用中」表示に戻し、Toast で通知する

### お支払い方法の管理

* 「お支払い方法を管理」ボタン（`has_payment_method=true` のときのみ表示）→ POST /api/v1/subscription/portal → 返された URL へ**同一タブで遷移**する
* カード情報の変更・請求先情報・請求書の確認は Stripe カスタマーポータルで行う。RB 側には同等の画面を作らない
* まだ Stripe Customer が無い場合はサーバが 422（「お支払い情報がまだ登録されていません。」）を返すため、ボタン自体を出さない

### 復帰時のクエリパラメータ処理

| パラメータ | 挙動 |
|------|------|
| `?checkout=success` | 成功 Toast（「お手続きが完了しました」）を表示し、GET /api/v1/subscription と GET /api/v1/auth/me を再取得する |
| `?checkout=cancel` | info Toast（「お手続きを中止しました」）を表示する。契約状態は変わらないため再取得は不要 |
| `?checkout=portal` | カスタマーポータルからの復帰。Toast は出さず、GET /api/v1/subscription と GET /api/v1/auth/me を再取得する |
| なし | 通常表示 |

* **契約の反映は Stripe の webhook 経由のため、`?checkout=success` で戻った直後にはまだ反映されていないことがある**。再取得しても契約が確認できない場合は「反映まで少し時間がかかる場合があります。しばらくしてから再読み込みしてください」の注記＋再読み込みボタンを表示する（エラー扱いにしない）
* `success_url` には `session_id` が付くが SPA では使わない。契約内容の取り込みは webhook（`checkout.session.completed`）が行うため、画面から Stripe を直接参照しない
* 処理後は `router.replace` でクエリパラメータを除去し、リロードで Toast が再表示されないようにする

## API

* GET /api/v1/subscription（現在の契約＋有効プラン＋機能フラグ＋プランカタログ）
* POST /api/v1/subscription/checkout（`{ plan }` → Checkout の URL）
* POST /api/v1/subscription/portal（→ カスタマーポータルの URL）
* POST /api/v1/subscription/change-plan（`{ plan }`）
* POST /api/v1/subscription/cancel
* POST /api/v1/subscription/resume
* GET /api/v1/auth/me（プラン変更・解約・復帰後に `plan` / `features` を取り直す）

POST /api/webhooks/stripe は Stripe からのサーバ間通信で呼ばれるため、SPA からは呼ばない。

Pinia の新ストアは追加せず、ページローカル state で管理する（契約状態は auth ストアの `user.plan` / `user.features` 経由で他画面へ伝わる）。

## Actions

* プランの契約開始（Checkout へ外部遷移）
* プラン変更（確認ダイアログあり）
* 解約（確認ダイアログあり）
* 解約の取り消し
* お支払い方法の管理（カスタマーポータルへ外部遷移）

## 状態

| 状態 | 表示 |
|------|------|
| ローディング（初期取得中） | 現在のプランカード・プラン一覧を Skeleton 表示 |
| 未契約 | 現在のプランカードに案内を出し、プラン一覧の全カードを選択可能にする |
| 利用中 | 現在のプランカード＋プラン一覧（契約中のカードは「ご利用中」で無効） |
| 解約申請中 | 警告 Tag＋利用可能期限＋「解約を取り消す」。プラン変更は引き続き可能 |
| 支払い注意（past_due / unpaid / incomplete） | 最上部に警告バナー＋「お支払い方法を管理」 |
| エラー | 取得失敗時はエラーメッセージ＋再読み込みボタン |

* 送信中（Checkout・プラン変更・解約・解約取消・ポータル）は該当ボタンをローディング表示＋無効化する

## エラー時挙動

* 422（すでに契約中／すでにこのプランを契約中／すでに解約申請済み／解約は申請されていません／お支払い情報が未登録）: Toast でサーバのメッセージを通知し、GET /api/v1/subscription を取り直して画面を実際の状態に合わせる
* Stripe の設定不備・API 障害（500）: 「お手続きを開始できませんでした。時間をおいて再度お試しください」を Toast で通知し、外部へ遷移しない。Stripe のエラー詳細は画面に出さない
* 取得失敗時はエラーメッセージ＋再読み込みボタンを表示する
* プラン変更・解約・解約取消の成功は Toast で通知する
