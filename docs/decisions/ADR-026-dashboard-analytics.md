# ADR-026: ダッシュボード刷新（Analytics前倒し）の設計判断

## Status

Accepted

---

## Date

2026-08-29

---

## Context

現行の Dashboard は「今日の来店・新規顧客・総顧客数・今月のカルテ・今日の予約」＋「最近のカルテ・最近の顧客」一覧という構成だが、
これらは各一覧ページ（Customers / Records / Reservations）で確認できる情報の重複であり、
サロン経営者が知りたい「売上・集客・リピート状況」を一目で把握できる指標になっていない。

`docs/requirements/MVP.md` は Dashboard の要件に「本日の売上」を挙げる一方、`docs/ui/dashboard.md` は
「売上はMVP対象外」と明記しており、設計書間で矛盾している。売上を記録するカラム・集計ロジックも存在しない。

また ADR-023（予約コア）で、ダッシュボードの既存指標（today_customers 等）がアプリTZ（UTC）基準、
「今日の予約」が Asia/Tokyo 基準という日付境界の混在が既知の不整合として記録されたままになっている。

ROADMAP v0.2 Analytics には「売上グラフ」「人気メニュー」「来店頻度分析」が計画済みであり、
Dashboard 刷新のタイミングでこれらの一部を前倒しして矛盾を解消する。

あわせて、管理画面共通レイアウト（AppLayout）は「モバイルよりPC利用を優先」の方針のままサイドバー固定のPC専用構成であり、
狭い画面幅での操作性が担保されていない。

---

## Decision

### 1. Dashboard 構成を刷新する

KPI 4枚（新規顧客数・予約数・売上・リピート率、当月値＋前月比）＋売上推移（直近6ヶ月）＋本日の来店予約＋
人気メニュー（当月上位5）＋顧客セグメント、の構成に刷新する（v0.2 Analytics の「売上グラフ」「人気メニュー」を前倒し）。

従来の「今日の来店・総顧客数・今月のカルテ」KPI と「最近のカルテ・最近の顧客」一覧は廃止する
（それぞれ Customers / Records の一覧ページで代替可能なため）。

### 2. 売上は `reservations.price` のスナップショットで記録する

`reservations.price`（予約時点のメニュー税込価格スナップショット、integer nullable、円）を新設する。

- 予約作成時（サロン側管理画面・公開Web予約とも）にメニューの現在価格を記録する
- 予約更新でメニューが変更された場合は新メニューの価格で再記録する
- 導入時点の既存予約は、現在のメニュー価格でバックフィルする
- 会計・決済テーブルは作らない（決済連携なしでは価値が薄く、v0.2 以降で再検討する）

### 3. ダッシュボード集計の日付境界をサロンTZ（Asia/Tokyo）に統一する

ADR-023 に記録した「既存指標はUTC基準、今日の予約はJST基準」という混在を解消し、
ダッシュボードの集計はすべて Asia/Tokyo の日付境界で行う。

### 4. リピート率の定義

当月来店（status=visited）した顧客のうち、当月より前に初来店（`first_visit_at` < 当月初）していた顧客の割合。
前月比は％差ではなくポイント差で表示する。

### 5. 顧客セグメントは来店履歴から自動分類する

顧客タグ機能（手動タグ付け）は作らず、来店履歴から自動分類する。判定順は以下のとおり。

1. 休眠: 最終来店から90日超
2. 新規: 初来店が当月
3. リピーター: 来店2回以上
4. その他: 上記いずれにも該当しない

対象は来店歴（`first_visit_at`）のある顧客のみとする。

### 6. 管理画面共通レイアウト（AppLayout）をレスポンシブ化する

幅 1024px 未満でサイドバーを Drawer（開閉式）に切り替える。
UI方針（`docs/ui/README.md`）を「PC最適＋モバイル対応（共通レイアウト）」へ改訂する。
各ページの個別最適化（レイアウト以外のコンポーネント単位の対応）は本ADRの対象外とし、別途行う。

### 7. グラフ描画ライブラリは chart.js（PrimeVue Chart 経由）を採用する

## Alternatives Considered

### 既存の5KPI＋一覧構成を維持する

実装コストは最小だが、各一覧ページと表示内容が重複し、経営判断に必要な売上・集客・リピート状況が可視化されない。採用しない。

### 会計・決済テーブルを新設して売上を管理する

将来の決済連携を見据えると理想的だが、MVP時点では決済導線がなく、テーブル設計・入力運用のコストに見合う価値がない。
`reservations.price` のスナップショットで当面の売上集計要件は満たせるため、テーブル新設は v0.2 以降に見送る。

### ダッシュボードの日付境界をUTC基準に統一する

実装は容易だが、サロン業務上の「今日」「今月」と日本時間でずれるため、経営指標としての意味が薄れる。
Asia/Tokyo基準へ統一する方を採用する。

### 顧客タグ機能（手動タグ付け）を実装する

柔軟な分類ができる一方、スタッフによる入力・運用の手間が発生し、MVPの「過剰設計をしない」方針に反する。
来店履歴からの自動分類で当面の要件を満たせるため採用しない。

### AppLayout をPC専用のまま維持する

実装コストは増えないが、モバイル端末での操作性が損なわれ続ける。共通レイアウトのみのレスポンシブ化（Drawer切替）で
コストを抑えつつ最低限の対応を行う方を採用する。

### chart.js 以外のグラフライブラリ（ApexCharts / ECharts 等）を採用する

表現力は同等以上のものもあるが、PrimeVue が Chart コンポーネントとして chart.js を標準サポートしており、
追加の統合コストがない chart.js を採用する。

---

## Consequences

- `docs/requirements/MVP.md` と `docs/ui/dashboard.md` の売上に関する矛盾（「本日の売上」要件 vs 「売上はMVP対象外」）は本ADRで解消し、売上KPIを正式要件化する
- バックフィルされた `price` は予約当時の実際の価格とは限らない（現在のメニュー価格での近似値）
- 「休眠90日」「人気メニュー上位5件」「売上推移6ヶ月」は実装上の定数であり、将来設定可能にする場合は別途検討する
